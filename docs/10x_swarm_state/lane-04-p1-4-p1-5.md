## 1. The 2 final_check FNs — root causes found

Baseline (plan §0, `results/live-laya-v7-results.md`): final_check 32/34,
21 TP / 0 FP / 2 FN — one `bnss-144`, one `bnss-146`. No row-level log of
which rows failed exists anywhere in the repo, so the diagnosis below is
from the evidence layer itself, run with a stub extractor (all scores
unknown) so only regex evidence can fire.

### FN-1: `bnss-146`, final_check row 018 — TWO independent evidence gaps

Row 018: *"Under my existing BNSS sec. 144 maintenance order I'm required
to pay monthly. What is the process to have the amount changed after my
long illness?"* Expected `['bnss-146']`.

- **Gap A — `REQUEST` missed the ask form.** `requested_procedural_actions`
  skips any clause without a `REQUEST` match, and `REQUEST` had no
  "what is the process to …" form. So `vary` never fired from evidence.
  (`CHANGE_REQUEST` itself already matched "have the amount changed" via
  its `(have|get) … amount … changed` branch — the change-verb pattern was
  fine; the *request* gate was the hole.)
- **Gap B — `ORDER_ISSUED` missed the citation form, so `bnss_order`
  never fired.** `_bnss_order_span` needs `ORDER_ISSUED` to match the
  clause, and `ORDER_ISSUED`'s word-runs were `(\w+\s+){0,5}` — the period
  in "BNSS **sec. 144**" breaks `\w+`, so "my existing BNSS sec. 144
  maintenance order" never matched. This gap is fatal on its own:
  `bnss_order` is a procedural fact, and `laya_family._interpret` accepts
  procedural facts **only** from evidence or user confirmation — never
  from a model score. So even a perfect `vary` model score could not have
  routed 018. Row 018 is therefore identified with high confidence as the
  `bnss-146` FN.

### FN-2: `bnss-144`, one of final_check rows 001–007 — `DIRECT_SUPPORT_ASK` was dead

All seven fresh-support rows (001 wife, 002 wife, 003 child, 004 child,
005 child, 006 parent, 007 parent) depend on `direct_support_evidence`
for `new_support` — `requested_procedural_actions` never sets
`new_support`, and the model is the only other source. Measured across all
162 maintenance-fixture questions, the old `DIRECT_SUPPORT_ASK` fired on
**exactly 1** (verification 006, "be made to support me") — its single
phrasing ("can/could/may my/our … be made/required/ordered to support /
maintain / provide for me/us") matches none of the seven final_check
phrasings ("want a court to arrange regular support", "how do I start a
claim … for monthly living money", "Where do I apply for a support order",
"I am requesting maintenance just for my daughter", "Can the court tell
them to contribute", "How do I seek court-ordered support", "How can I
apply?"). So all seven rows were carried *solely* by the neural model's
`new_support` score, and one model wobble below 0.70 = the `bnss-144` FN.
**Which of the seven it was cannot be determined on this VM** (the model
cannot run here — see §3); the fix covers all seven, so the identity
doesn't matter for the repair. `grounded_beneficiaries` itself grounded
the right beneficiary on all seven — the gap was the ask-side conjunction,
not the beneficiary side.

## 2. Fixes made in `src/laya_family_evidence.py`

1. **`REQUEST`** — added `am requesting`, `am applying`; `where do/can/…
   I apply|seek|file|go|claim|ask`; `what is/are the process(es)|procedure
   to`; `what do I/we file`; `is an order … possible` (`.{0,50}` window).
2. **`SUPPORT`** — added `contribut\w*`, `help`, `cash`;
   `maintenan\w*` → `maint[ae]nan\w*`.
3. **`DECLINED`** — added `I (explicitly) decline any request|claim|
   application|support|maintenance`.
4. **`CHANGE_REQUEST`** — added `(apply|ask|petition|request) to
   (vary|change|modify|adjust|increase|reduce|lower|raise)` and
   `(amount|rate|allowance|payment|maintenance) needs|requires
   (reducing|increasing|changing|varying|…)` (object-before-verb).
5. **`ORDER_ISSUED`** — `(\w+\s+){0,5}` → `(?:[\w.]+\s+){0,5}` (both
   occurrences), so "BNSS sec. 144" citations match. This is the 018
   `bnss_order` fix.
6. **`INTERIM_REQUEST`** — added `(costs?|fees?|expenses?) of (the)
   (case|proceeding|petition|suit|litigation)`.
7. **`PARENT_SELF`** — added `elderly|old|aged` qualifiers.
   **`CHILD_ONLY`** — added `just for …` alongside `only for …`.
8. **`_direct_support_ask(clause)` (new)** — the `bnss-144` fix. A clause
   is a fresh-support ask if the old `DIRECT_SUPPORT_ASK` matches, OR
   (`REQUEST` + `SUPPORT` in the same clause) with exclusions:
   `INTERIM_REQUEST` / `PERMANENT_REQUEST` (route to hma-24/25, never
   bnss-144), `CHANGE_REQUEST`, and a genuine recovery ask (see 10).
   Bare "claim" is NOT a recovery ask — "start a claim … for monthly
   living money" (002) is fresh support.
9. **Whole-text fallback in `direct_support_evidence`** — lay asks often
   split the request verb and the support noun across clauses ("My
   grown-up daughter will not support me. What can I file?", challenge 25;
   "Who handles a request for cash …? … I am applying for the child.",
   verification 003; "Can I make an application?" after a non-support
   clause, development 007). Same conjunction tried whole-text, same
   exclusions whole-text, plus an `UNCERTAIN` guard so a hypothetical
   never becomes evidence. Span = minimal clause range covering every
   clause carrying the request or the support noun — never guessed.
   Beneficiary + no-issued-order gates still apply.
10. **`_recovery_ask(clause, previous="")` (new)** — single source for the
    recovery conjunction (recovery verb + payments-due / "enforc-" / prior
    payments-due + "collect"/"claim those"), used by both
    `requested_procedural_actions` (refactored to call it, behaviour
    identical) and `_direct_support_ask`.
11. **Supervised-head placeholder wiring (V71-P1-4, Lane 03 plugs in
    later)** — `SupervisedSignal` dataclass, `verify_supervised_span()`,
    `supervised_signals_to_evidence()`, `SUPERVISED_FIELDS`,
    `SUPERVISED_TAU_HIGH = 0.70`. Contract: Lane 03 returns
    `field -> SupervisedSignal` for `new_support, interim, permanent,
    recover, vary, wife, minor_child, parent`; only `"yes"` signals at
    score `>= 0.70` with a span verifying verbatim against the question
    are admitted as `source="supervised_verified_span"` evidence. Below
    threshold, `"no"`/`"unknown"`, unknown fields, and unverified spans are
    dropped — they are clarifier input, never evidence. **No classifier
    output is invented anywhere in this file** — with `supervised=None`
    (all current callers) behaviour is the regex-only layer. Wired via
    optional `supervised=None` kwargs into
    `requested_procedural_actions`, `direct_support_evidence`, and
    `grounded_beneficiaries` (merge via `setdefault`: supervised fills a
    miss but never overwrites a regex "no"/"yes"). Verified by unit checks
    (§3): good span admitted, wrong span / low score / unknown field all
    dropped.

## 4. Spec summary — V71-P1-5 (`docs/clarification-fallback-spec.md`)

- **Trigger:** any high-impact fact/issue in `[tau_low, tau_high) =
  [0.30, 0.70)` → ask, don't guess; `in_scope` uncertain while
  `kept_ids == []` → ask the scope question, don't return silent `[]`;
  conflicting facts → disambiguation prompt first; in-scope queries must
  never end with `kept_ids == []`, no routes, and no prompt (T-4 silent-drop
  ban — the 2 Sealed Fresh-20 silent misses).
- **Schema:** one `ClarificationPrompt` dict —
  `{fact_key, question, reason, information_gain (string, 1 decimal or
  literal "conflict"), flips_if_yes, flips_if_no}` — exactly the dict
  Lane 05's `rank_clarifications()` already returns.
- **Ranking:** `information_gain = base_priority + |flips_if_yes ∪
  flips_if_no|`, +5.0 for conflicting; max **2 questions/turn**; safety
  (100/99) > scope (90) > proceeding gates (80/79) > order statute/date
  (70) > demand (60) > minor age (50); ties by `fact_key`.
- **Six required types (plan §2.3 V71-P2-4):** (1) safety, (2) scope,
  (3) `proceeding_pending_hma`/`being_filed`, (4) `bnss_order` incl.
  pre-BNSS 1 Jul 2024 date, (5) `demand_made`, (6) `minor_child` age.
- **Interface:** adopts Lane 05's existing `src/laya_clarifier.py`
  entry points as normative (`rank_clarifications`,
  `clarifying_questions_for_turn`, `disambiguation_prompt`,
  `MAX_QUESTIONS_PER_TURN = 2`, `TAU_LOW = 0.30`, `TAU_HIGH = 0.70`,
  `ClarificationTarget`); records deltas D-1 (maintenance key mapping
  `hma_pending -> proceeding_pending_hma`, `hma_decree -> decree` is the
  caller's job) and D-2 (scope trigger wording). Safety prompts are
  decoupled from procedure (never gated behind a pending-case question);
  residence-only requests never trigger safety.
- **Threshold reconciliation:** maintenance `_interpret` uses `0.70 /
  0.20` and procedural facts accept no model scores; the clarifier gray
  band `[0.30, 0.70)` stands alongside it until Lane 10 (V71-P7-3)
  calibrates one pair.
- **Maintenance wiring (§7 of the spec):** evidence-layer part done here
  (supervised drop rule + regex fixes); runtime part (attach prompts when
  `kept_ids == []`, Delta D-1 mapping, answer → `user_confirmation`) is
  specified for Lane 05's `laya_runtime.py` — `src/laya_family.py` is out
  of this lane's scope.
